## 2. Refactor goal and success measurements

The target is **reduced duplicate authority and shorter, narrower change paths**, not a particular class/file count. Before any refactor, record which module owns each mutable object, which component writes every file, and which module decides eligibility for visual operations. A successful refactor makes an operation pass through one command and one relevant adapter, without switching logic among UI menus, drag handlers and separate authoring registries.

**Acceptance measures:** no regression in all existing tests; every new behavior has a golden fixture, negative semantic tests and native Qt evidence when applicable; no new import cycles; no Qt dependency in domain/language code; no second writable graph registry; no second unguarded file writer; no additional ad hoc Python operation selection in `gui.py`; baseline work preserved through every failed save, external-change conflict and migration; measurable reduction in *duplicated conditional paths*, not merely LOC.

**Scoping rule:** one ticket = one responsibility boundary + one vertical user behavior + its tests. If a patch spans document lifecycle, graph compiler, widget rewrite, installer and new language in one change, reject and split.

## 5. Proposed subsystem boundaries and anti-boundaries

### Document service (new when justified)

Should own: register/open/close docs; `get_snapshot`; apply transaction; undo/redo grouping; dirty/saved state; external-change check; publish/rollback; revision-tagged results. Should **not** parse Python, mutate QPlainTextEdit, own graph nodes, or write without persistence API. Begin with one source document and two views to prove this boundary. Prefer a small registry of document sessions, not an abstract enterprise data layer.

### Program graph domain (new when justified)

Should own: schema validation, immutable graph snapshots, pure transactional commands, undoable node/edge/scope edits, deterministic save/read. Does **not** own running code, graphical camera, or Python-specific rules. Its structural validator can insist that IDs and endpoint references exist. Its semantic validator may allow incomplete nodes and unexpected type combinations with diagnostics. A formal failed connection can be preserved as an explicit diagnostic draft intent, not a corrupt raw edge.

### Python lowering (new when justified)

Should own: supported operations' lowering to structured Python semantics, dependency closure, scope/order/type/effect checks, source mapping and compiler diagnostics. Should consume immutable ProgramGraph revision and return a candidate and diagnostic facts; **cannot** publish bytes. Neither `python_edit` nor `python_lowering` may directly mutate Qt state. The new module is justified only if v2.50's source-transform pipeline cannot reasonably own graph-to-code lowering without conflating responsibilities. Existing Python operation definitions should be reused, not duplicated.

### Reconciliation/mapping (defer until proof)

Should own: comparison of base/current graph/current text, importable text diffs and conflict classification. Initially function-scoped. Preserve unsupported source islands. Defer any general three-way merge framework until a two-function round-trip demonstration proves its need. If added, it may only use shared provenance and adapter results, not untrusted heuristic identity matching.

### NO new frameworks by default

No event bus, CQRS framework, plugin marketplace, universal AST/bytecode engine, custom debugging protocol, alternate filesystem writer, Redux-like duplicate store, separate app shell, or graph interpreter. Introduce an adapter interface only when a second implementation or real test double demonstrates what it must abstract.

## 7. Exact cleanup method for oversized functions

### `python_graph.py::_body_graph` / nested `emit_sequence`

1. Capture canonical fixtures for straight-line returns, if/elif/else, loops, break/continue, nested functions, classes, call evaluation, exceptions, short-circuit, async, closures, Unicode and source spans.
2. Identify pure responsibilities already present (scope indexing, expression nodes, control/effect evidence, boundary edges, layout hints). Make one pure extraction at a time, preserving node/port/edge IDs and order where contract demands.
3. After each extraction, diff **serialized graph descriptors**, not screenshots alone. Verify no new/control/data edges and no silent missing source regions.
4. Keep provenance on every source-derived edge. Opaque constructs remain opaque if not understood.
5. Prefer local pure functions within existing module until abstraction is used elsewhere; do not prematurely create generic SSA/CFG framework.
6. Only then consider splitting `python_graph.py` into cohesive files if meaningful independent responsibilities and no cycles can be demonstrated.

### `gui.py::_create_qualified_operation`

1. Inventory all supported operation IDs, input forms, field validation, default-value controls and dispatch handlers; golden native UI interactions.
2. Derive form schema from the existing operation definition or a small adapter-owned `FormSpec`, preserving per-operation dynamic eligibility.
3. UI renders fields, supplies parameters to one command dispatcher; Python adapter validates before persistence. Prevent UI from assembling Python string patches.
4. Extract shared form scaffolding only if 2+ existing operations prove same contract; retain specialized widgets for unusual operations.
5. Remove old dispatch branches only when equivalence tests prove no other caller still uses them. No temporary second generic builder lingering after migration.

### `python_authoring.py` / `python_edit.py`

1. Do not rewrite safety gates merely to shorten methods. Extract pure reusable proof helpers only with semantically adversarial tests (effectful calls, binding dominance, keyword args, control-flow edges, duplicates).
2. Consolidate duplicate eligibility where it already exists: one adapter source of truth; UI and operation catalog consume it.
3. **Preserve strict refusals** for unknown side effects and unsupported source contexts. Do not relax safety to make UX demonstrations pass.
4. Keep source proposal calculation separate from committing disk bytes. The latter must remain backup/preimage/external-check guarded and eventually operate from the document session.
5. Use stable operation IDs, explicit versioning and a compatibility map when renaming or reorganizing operations.

### `qt_smoke.py::main`

1. Extract test stages, not test expectations. Each stage has a stable ID, one timeout budget, input, assertions, and screenshots/log names.
2. Capture uncaught Qt slot exceptions in the harness, fail the process even when a stage superficially reaches end.
3. Event-loop waiting must be bounded; modal dialogs have safe test teardown and failure diagnostics.
4. Keep the existing `RUN-ALL.sh` as the release entry point until a replacement demonstrates identical failure behavior. Never report `NATIVE_QT_SMOKE_PASS` on a timeout or callback traceback.

## 8. Cleanup categories: eliminate, consolidate, or defer

**Eliminate after parity tests:** duplicate GUI-side source-kind pin whitelists; duplicate dirty state copies; catalog action count constants; unreachable legacy navigation branches if no live callers; parallel disk writer; redundant source preview builders with distinct refusal logic; stale comments claiming prototype data is executable. **Consolidate:** action definitions and context filters; source proposal/save and undo journal; document tab identity and routing; graph validation vs diagnostic emission; source-to-graph snapshot versioning. **Keep intentionally separate:** executable ProgramGraph and read-only GraphDescriptor; source-owned and graph-owned authority; structural vs semantic validation; browser prototypes and programming operations; resource and source data relations; prototype file format and new graph file format. **Defer:** plugin API, second language, general SSA, arbitrary CFG restructuring, general partial-function publish, complex overlapping sync merge, remote execution, graph runtime, arbitrary UI theme refactor, layout redesign.

## 9. Data migration and deletion governance

Before deleting or merging any module: (a) enumerate callers and tests, (b) identify authoritative replacement and versioned contract, (c) add backwards-compatibility fixture, (d) migrate one path, (e) remove old path only after caller count is zero, (f) retain rollback artifact, (g) update docs/decision register. Deprecated adapters may exist temporarily behind a documented expiry milestone but may not create a second source of truth. All retired code must be removed **after** proof, not left as an alternate runnable path.

Graph v1 schema must have explicit migrators and a future-version policy. Do not overwrite unknown future-version documents with a downgraded serializer. Use read-only recovery/export and preservation of raw bytes. Legacy `model.py` remains compatible; importing legacy prototype controls to executable operations is an explicit user decision only when adapter rules establish meaning.

## 10. Risks, regressions, stop conditions

| Risk | Impact | Early detector | Required reaction |
|---|---|---|---|
| Native Qt regression masked by unit tests | Critical UX | Host smoke, callback exception log, screenshot | Block promotion; preserve known-good install |
| Text/session split ownership | Critical data loss | Two-tab unsaved edits and switching test | Revert duplicate holder; enforce session single owner |
| Graph compiler drops reachable invalid operation | Critical semantic corruption | Dependency/side-effect golden tests | Block publish entirely; keep last-good output |
| Effectful expression executed twice | High runtime change | Stateful call test counters | Reject lowering optimization; add binding/materialization |
| Wrong source span/Unicode conversion | High editing corruption | UTF-8/UTF-16 CRLF test corpus | Refuse edits on uncertain source mapping |
| Generation status stale or conflicts ignored | High wrong program | Interleaved graph/text/FS revision tests | Conflict+preserve both, never silent overwrite |
| Broad splitting creates circular imports | High debt | AST import graph and architecture tests | Revert/scope smaller; move types to proper owner |
| Large event/main method refactor hides failures | High false qualification | Fault-injection modal/callback tests | Keep old fail-closed harness until equivalent |
| Untrusted project executes during open | Critical trust | Mock executable sentinel in input | Block automatic execution and demand user action |
| New CLI/installer disrupts user project | High data loss | Isolated install rollback test | Don't promote; retain previous version and logs |

Stop an implementation and request architecture review when a proposed change creates another canonical buffer/graph registry, another authoring operation registry, another unguarded writer, a custom general-purpose compiler framework, a UI-owned Python semantic rule, or a source regeneration that can silently discard unknown constructs. Stop a phase when a new test demonstrates semantic mismatch even if all previous tests pass.

## 11. Refactor acceptance gate per ticket

Each ticket must deliver: precise baseline commit/archive hash and environment; touched owner+contract; at least two implementation choices and reason selected; pre-change failing/characterization tests; behavior/semantic diff; exact tests run and results; native Qt evidence or BLOCKED label; old path removal or explicit deprecation; rollback/recovery; updated ownership map, decision log, requirements mapping, and stage status. Migrations are **incremental and reversible**. Regression repairs must use underlying owner, not GUI bypasses or compatibility shims with indefinite lifetime.

## 13. Definition of a healthy refactor

A good change **removes an architectural ambiguity**, shortens the journey from user intent to one authoritative semantic edit, and makes verification easier. A bad change merely moves hundreds of lines, adds additional stores/registries, or exposes new toggles to mask uncertain behavior. Prefer a smaller program that honestly refuses unsafe generation over a large program that creates plausible but incorrect `.py`.
